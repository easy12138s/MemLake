## 四、疑似逻辑缺口（已修复）

**approval/conflict.py `_detect_exact_key_conflicts` 的候选域与 `detect_conflicts` 不一致。**

- 原计划推断「project_id=None 时 SQL 编译为 `project_id = NULL` 恒为 false、L0 对悬浮需求完全失效」——**该机制描述不准确**：SQLAlchemy 会将 `column == None` 规范化为 `column IS NULL`，因此 L0 对悬浮需求并非失效，而是只在 `project_id IS NULL` 的悬浮节点之间判定。
- 真正的缺口是**方向相反的漏检**：`detect_conflicts` 的向量召回路径对悬浮需求按 `system_id` 收口候选域（conflict.py:112-113），而 `_detect_exact_key_conflicts` 的查询条件**完全没有 system_id 过滤**。后果：悬浮需求与同 system 下已入项目节点之间「关键标识完全相同」的硬冲突会被 L0 漏检。
- 另有次要不一致：`_detect_exact_key_conflicts` 签名标注 `project_id: uuid.UUID`（非 Optional），但调用方实际可传 None。
- **修复（用户已确认）**：L0 查询条件改为与 L1（FilterSpec/compile_sqlalchemy）完全镜像——`project_id`/`system_id` 非 None 时各自过滤、None 时不过滤该维度；签名改为 Optional 并新增 `system_id` 参数。修复后悬浮需求按 system_id 收口候选域，与同 system 下已入项目节点的关键标识硬冲突可检出；跨 system 不再误判。新增集成测试 `test_floating_l0_detects_project_node_same_system`（含正向检出 + 跨 system 负向用例）。
