## 数据备份与恢复

备份覆盖关系表、AGE 图数据、pgvector 向量与 ag_catalog 元数据（`pg_dump -F c` 自定义格式）。

```bash
cd deploy
./backup.sh                        # 备份到 backups/（默认保留 30 天）
./backup.sh /path/to/dir           # 指定目录
RETENTION_DAYS=14 ./backup.sh      # 自定义保留期

./restore.sh                       # 恢复最新备份（停 mem-lake → 重建库 → 恢复 → 重启）
./restore.sh backups/memlake_20260808.dump
```

定时备份（每日 2:00，保留 30 天）：

```bash
sudo cp deploy/memlake-backup.cron /etc/cron.d/memlake-backup
sudo chmod 644 /etc/cron.d/memlake-backup
```

误操作防护：`docker compose down` 不带 `-v` 不删数据卷；恢复流程见 [DEPLOYMENT.md](../../DEPLOYMENT.md) 数据备份章节。

## 监控

### /metrics 端点

| 端点 | 内容 |
|------|------|
| `http://<host>:8000/metrics` | MCP 网关指标 |
| `http://<host>:8001/metrics` | Embedding 服务指标（embed/rerank 调用数、耗时、输入规模） |

内网 Prometheus 直接抓取；公网暴露需自行加防护层。

### 核心指标族（`src/mem_lake/observability/metrics.py`）

| 指标 | 类型 | 含义 |
|------|------|------|
| `memlake_mcp_tool_calls_total{tool,status}` | Counter | 工具调用量与成功/失败 |
| `memlake_mcp_tool_duration_seconds{tool}` | Histogram | 工具耗时 |
| `memlake_approval_batches_total{status}` | Counter | 审批批次终态（含宽松模式 approved） |
| `memlake_search_engine_duration_seconds{engine}` | Histogram | 三引擎（vector/fulltext/graph）各自耗时 |
| `memlake_search_phase_duration_seconds{phase}` | Histogram | 混合检索分阶段耗时（embed/vector/fulltext/graph/fuse/rerank）——A5 黑盒拆解 |
| `memlake_vector_probe_path_total{path}` | Counter | 向量检索路径：`window`=HNSW 行扫收敛 / `exact`=聚合精确兜底；exact 占比骤升即该 REINDEX |
| `memlake_embedding_calls_total{op}` / `memlake_embedding_duration_seconds{op}` | Counter/Histogram | embedding/rerank 调用与耗时 |
| `memlake_rerank_fallback_total` | Counter | 精排降级回退 RRF 次数 |

## 向量索引维护（手动，不设定时任务）

HNSW 索引随写入碎片化后，向量检索从 `window`（行扫+top-N）退化为 `exact`（全表聚合慢路径）。以 `memlake_vector_probe_path_total{path}` 的 exact 占比为信号，在**低峰期手动**触发 admin 工具 `reindex_project_vectors`，再用 `get_reindex_status(task_id)` 轮询进度（状态机 pending→running→done/failed）；大批量导入后也建议主动触发一次。无需 cron。

## 测试残留清理（手动命令，文档化）

共享 dev 库会被 e2e/集成测试污染（随机 system、测试项目、孤儿向量）。**保留域是环境相关的真实数据标识，不写入公开 wiki**——执行前用 `SELECT id, name FROM "system"` 与本地运维记录（ignored `docs/plan/`）确认本环境的真实 system 名称与项目 UUID；至少保留一个业务 system 与承载真实游离知识的项目。

先干跑清点、人工核对数字，再决定是否执行：

```bash
# dry-run（默认，只清点不删）——下例 <...> 占位符按本环境真实值替换
.venv/bin/python -m scripts.cleanup_test_leftovers \
  --keep-system <业务system名称> --keep-system <另一保留system> \
  --keep-project <真实项目UUID1> --keep-project <真实项目UUID2>

# 确认无误后执行（同一组保留参数 + --execute）
.venv/bin/python -m scripts.cleanup_test_leftovers ... --execute
```

脚本口径：删保留域外的节点/向量/AGE 顶点/测试 system/批次/重嵌任务；**audit_log 与 access_key 不动**（append-only 与凭据不可推断）。执行后内置复核：保留域计数一致、无残留 system/悬空引用。此前运维已据此清理 380 测试节点 / 46 测试 system。不装 cron——每次跑测试套件后按需手动干跑。

**批次保护加固（2026-11-26）**：脚本原口径按 `project_id` 判定批次归属，而**悬浮需求的批次 `project_id` 为空**，会被当成「不保留」一并删除（实测 55 个真实悬浮批次 / 68 个审批项指向保留域节点）。脚本已补一条**节点归属维度**的保护：审批项 `target_id` 命中保留域节点（system ∈ 保留 或 project ∈ 保留）的批次一律保留。改动在本地脚本（scripts 不入库），换环境重建脚本时需同步这一段。

**access_key 残留要单独处理**：脚本按设计不碰凭据，而集成测试会批量造 Key（本次残留 1288 个未具名 active Key：dev 1054 / pm 231 / admin 3，其中 3 个 admin Key scope 为空＝不受限访问、2 个 dev 触及真实 system、1281 个指向已删除的测试项目）。清理顺序：**先清数据、后吊销 Key**（否则 Key 仍能对已删项目写入）。判定口径为 `name IS NULL`（真实 Key 一律登记 name/owner），逐个 `revoke_access_key(key_id=...)`——吊销不删行，保留审计与历史关联。

**2026-11-26 一次完整清理留档**：删除 2070 节点（ProjectProfile 769 / CodeSnippet 892 / Requirement 275 / Solution 86 / Pitfall 48）+ 2070 图顶点 + 14726 孤儿向量 + 50 个测试 System + 48 条 SystemProject + 4092 计数器 + 539 批次（item 级联）+ 699 重索引任务；另吊销 1288 个测试 Key。保留域快照执行前后完全一致（中方诊药云系统 1398 节点 / MemLake 7 节点），残留 System 0、悬空 system 引用 0、悬空向量 0；清理后待审批队列为 0，真实 5 个 Key 全部可用。

**守卫：保留 system 的关联项目默认受保护**（2026-11-26 加固，源于 11-20 误删事故）：`system_project` 映射（system↔项目归属）是「该项目属于该系统域」的权威口径，其下节点默认**不删**，只有 `--drop-project <uuid>` 显式点名才放开。11-20 那次清理只列了 `--keep-project 7e81667e/0abd0149`，而「中方诊药云系统」关联的另外 3 个真实项目未列 → 删除谓词（system∉保留 AND project∉保留）把这三个项目的全部 project-scoped 节点连锅端（见下文事故记录）。dry-run 会打印三段清单：受保护项目总数 / 靠守卫兜住的（未显式 `--keep-project`）/ `--drop-project` 显式删除的——**执行前必须逐条核对**。

**备份（2026-11-26 起才有）**：`deploy/backup.sh` 产出 pg_dump 自定义格式全库备份（含 AGE 图 + pgvector + 关系表），落到 `deploy/backups/`（已 gitignore，保留 30 天）。已装**用户级 crontab**：每日 02:00 执行（`crontab -l` 可见）。此前该环境**从未产生过任何备份**——这正是 11-20 误删无法回滚的直接原因。清理脚本执行前先确认有当天的 dump（`ls -t deploy/backups/ | head -1`），恢复见 `deploy/restore.sh --yes backups/<file>.dump`。

### Access Key scope 被测试污染（故障模式与恢复）

**症状**：真实团队的 dev/pm Key 突然「找不到自己的项目」（工具报「项目 X 不在当前 Access Key 的项目范围内」），或该团队后续提交的内容**落进了测试项目**；审计里能看到 `action=update_scope` 且命中范围异常。

**根因**：集成测试直打生产库，`update_access_key_scope(role_filter="dev")` 会批量改写**全库同角色** Key 的 `project_scope`（2026-11-26 实测：真实 Key「中方诊药云系统-dev」被改成测试项目，其后提交的 19 个真实业务节点 + 19 条边全部落错位置）。

**恢复步骤**：

1. **回溯原始 scope**（审计可查，创建后的第一条即原值）：

   ```bash
   docker exec deploy-postgres-1 psql -U memlake -d memlake -x -c \
     "SELECT created_at, actor, action, detail FROM audit_log
      WHERE action='update_scope' AND target_type='access_key'
      ORDER BY created_at;"
   ```

2. **admin 恢复 scope**：`update_access_key_scope(key_ids=["<key_id>"], project_scope=[...])`
   ——**必须显式传 `key_ids`**，绝不用 `role_filter` / `grant_all_projects`；该工具只改项目清单，**不影响 `systems` 授权**（恢复后需复核 `project_scope` JSON 里的 `systems` 仍在）。

3. **迁移已落错项目的节点**：MCP 无「改研发资产归属」的工具，需走仓储层 `knowledge.repository.set_node_project`（SQL + AGE 顶点同事务同步、`version+1`、写审计、**不重算向量**——facet 文本不含 project_id）。边不携带 project_id，随端点自动跟随；迁移后核对「声明的边数 == AGE 实际边数」。

4. **清队列**：测试残留批次用 `review_reject` 统一退回，`review_comment` 注明「集成测试残留，非真实提交」，避免真实待审被淹没。

5. **根治**：见 [项目演进](07-项目演进.md)「未来优化点」——集成测试独立数据库（`TEST_DATABASE_URL`）。

## 历史研发资产被清理脚本误删（2026-11-20 事故）

**症状**：11-12 反馈 ISSUE-19——「09-28 批 16 个节点检索不到」；深查发现同一批真实研发资产（云HIS 门诊服务/商城/医保绑定域）在系统里整体消失。指纹特征：**需求（system-owned）全在，研发资产（project-scoped）成片消失**；现存 project-scoped 节点全是 2026-11 的，而 2026-09/10 存活的全是需求——这正是「按 system 维度判归属」的删除谓词形状。

**根因链（四环，均有审计证据）**：

1. `2026-09-28 07:10:54` dev Key `d6a84a62` 提交 16 个研发资产到项目 `01276605`（门诊服务），批次 `edfc6e95` 即时审批通过，22 条边挂到 8 个存活需求（`implements` 4 / `references` 18）——**当时数据正常入库**。
2. `2026-09-28 08:48:43` 集成测试用 `update_access_key_scope(role_filter="dev")` 把 **75 个 dev Key 全量改写到测试项目** → 团队 dev 看不到门诊服务项目 → 11-12 报的「检索不到」（与 11-26 同类事故，只是范围更早）。
3. `2026-11-20 07:15:31` 清理脚本以 `--keep-system 中方诊药云系统 --keep-system MemLake --keep-project 7e81667e --keep-project 0abd0149 --execute` 执行，**漏列保留 system 的关联项目** → 删除谓词（system∉保留 AND project∉保留）清空门诊服务/商城/需求关系域全部 project-scoped 节点。
4. `2026-11-26` 再次清理时删掉了已孤立的批次行与 `approval_item.payload` → **正文原文在库内不可恢复**，只剩审计里的标题/类型/边结构。

**损失清单（据 audit_log 逐条比对现存节点）**：真实域共丢 **64 节点 / 111 条边**（两端皆失 83、一端存活 28）——门诊服务 16、商城 44、医保绑定域 3、需求关系域画像 1。

**恢复口径**：重建清单（64 节点 + 111 边，含原 node_id / 项目 / 类型 / 标题 / 提交人 / 边端点）由审计导出，作为 dev agent 从代码库重新沉淀的唯一依据。本轮决定**暂不回填**——正文不可从库内恢复，占位回填只会把假知识塞回检索面；只做防复发 + 留档。

**防复发（三件套）**：① 清理脚本守卫（保留 system 关联项目默认保护 + `--drop-project` 显式放开）；② 每日备份 cron（此前从无备份，误删不可回滚）；③ 集成测试独立数据库（见[项目演进](07-项目演进.md)「未来优化点」）。

## 噪声节点归档口径（冒烟/测试残留）

库里**没有软删工具**：`knowledge_node.is_deleted` + `status='archived'` 有字段、检索层也按 `status='approved' AND is_deleted=false` 过滤，但没有任何 MCP 工具/代码路径写入这两列——所以「清理噪声节点」目前只能走运维 SQL。推荐口径（2026-11-26 已按此归档 6 个冒烟节点：1 Solution + 5 Requirement）：

- **软删**：`UPDATE knowledge_node SET is_deleted=true, status='archived', version=version+1 WHERE id IN (...)`——保留库内行与 created_by/version 供追溯，不物理删除；
- **清派生件**：删 `node_embedding` facet 行 + AGE 顶点（`DETACH DELETE`，连带边）——只软删 SQL 行的话，图遍历/全文路径仍可能命中；
- **留痕**：`audit_log` 追加 `action='archive'` 行（append-only，不改历史行）。

判定口径：`tags` 含 `smoke` 或标题带 `【冒烟】` 前缀的节点即测试残留（真实知识一律不打 smoke 标签）。归档后以 `get_node_info` 复核（`found=false` + `is_deleted=true`）并确认检索不再命中。

## 日志

结构化日志（structlog），`OBS_LOG_FORMAT=json` 输出单行 JSON（生产推荐），每条工具调用贯通 `request_id / operation_id / actor / project_id` 上下文。

```bash
docker compose logs -f mem-lake           # 实时
docker compose logs --tail 100 mem-lake   # 最近 100 行
```

中间件按调用输出 `TOOL_CALL actor=... tool=... status=... duration=...ms op_id=...` 单行摘要，可用 grep/jq 快速过滤。

## 版本更新

```bash
git pull
docker compose up -d --build
```

Schema 变更由 Alembic 迁移管理（`alembic/versions/`），mem-lake 容器 CMD 启动时先执行 `alembic upgrade head`（幂等），应用再校验 `alembic_version` 与脚本 head 一致（不一致拒绝启动，日志给出处置命令）；新增列用 nullable 无默认值在线加列避免表重写。`create_tables()` 仅作 v1.0.x 过渡期兜底；tsvector 触发器由 `init_knowledge_schema()` 存在性守卫幂等处理（已存在则跳过 DDL，缺失才重建，避免长读事务卡死启动）。存量 v1.0.0 首次升级需先 `alembic stamp 0001_initial` 登记基线（见 DEPLOYMENT.md「更新版本」）。单容器重启即可：`docker compose up -d --build --no-deps mem-lake`。

## 故障排查索引

| 症状 | 入口 |
|------|------|
| 容器启动失败 | `docker compose ps` + 各容器 logs；postgres 首建 10-15 分钟属正常；embedding 健康检查失败先查模型挂载 |
| 认证失败 | 请求头带 `X-MCP-Key`；查 Key 状态 active；明文丢失只能重新创建 |
| 团队 Key 突然访问不到自己的项目 / 内容落到测试项目 | 见上文「Access Key scope 被测试污染」：先用 audit_log 回溯原始 scope，再 admin 显式 `key_ids` 恢复 |
| 真实研发资产突然大面积检索不到 / 需求在但资产没了 | 见上文「历史研发资产被清理脚本误删」：用 audit_log 的 write 记录与现存节点做差集，确认是否被清理脚本删掉；恢复走备份或按重建清单从代码库重沉淀 |
| 检索结果里混进测试占位节点 | 见上文「噪声节点归档口径」：软删 + 清向量/图顶点 + 审计留痕 |
| 连接池耗尽（`QueuePool limit reached`） | 调大 `DATABASE_POOL_SIZE` / `DATABASE_MAX_OVERFLOW` 重启 |
| 数据误删 | `./restore.sh --yes backups/<file>.dump` |

完整排查步骤见 [DEPLOYMENT.md](../../DEPLOYMENT.md) 故障排查章节。
