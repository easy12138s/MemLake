# 项目定位与核心概念

> 上一步：[首页](Home.md) · 下一步：[架构与实现](02-架构与实现.md)

## Mem Lake 解决什么问题

软件研发团队普遍在用 AI 编程工具，但知识是割裂的——每个 AI 只记得自己会话里发生的事。Mem Lake 把这些割裂的记忆汇成一份团队共享的知识图谱：

- **PM 的 AI** 发布需求（含验收标准、优先级、关联关系），自动进入审批流；
- **开发的 AI** 提交代码片段、实现方案、设计意图、踩坑记录，自动挂到对应需求上；
- **任何人（以及任何人的 AI）** 都能检索这份图谱：查相似需求、看需求上下文、分析影响范围、检索代码与方案。

关键在于**零额外维护成本**：知识由各角色的 AI 在正常工作中自动沉淀，不需要专人整理文档，也不需要为知识库单独养一个 Agent。

## 核心概念

### 知识节点（7 类）

| 类型 | 内容 | 必填属性 |
|------|------|---------|
| `ProjectProfile` | 项目画像：技术栈、架构、约定 | name、description |
| `Requirement` | 需求：编号、优先级、模块、验收标准 | requirement_id、priority、module |
| `CodeSnippet` | 代码片段：类/函数的职责与位置 | name、type、responsibility |
| `Solution` | 实现方案：采用的做法与备选 | approach、version |
| `DesignIntent` | 设计意图：为什么这么做 | rationale |
| `Decision` | 架构/技术决策 | decision_id、decision |
| `Pitfall` | 踩坑记录：症状、根因、解法、严重级 | symptom、root_cause、solution |

属性在写入前经 schema 校验（`src/mem_lake/knowledge/schema.py`），必填字段缺失直接拒绝，保证图谱内容质量。

### 关系边（12 类）

节点之间通过有向边关联：`implements`（需求←代码）、`depends_on`（代码间依赖）、`realized_by`（代码→方案）、`embodies`（方案→设计意图）、`traces_to`、`conflicts_with`、`duplicates`、`relates_to`、`supersedes`、`version_of`、`described_by`、`references`。

边的价值在于**关系即上下文**：拿到一个需求节点，AI 能沿边找到实现它的代码、代码背后的方案、方案体现的设计意图——这是传统文档库给不了的。

### 项目与 system 域（双归属模型）

- **项目（project）**：资产层隔离单位。代码片段、方案等开发产物归属具体项目，dev 按 project scope 隔离。
- **system 域**：需求层隔离单位，由 admin 统一创建并挂接项目。需求（Requirement）必须归属一个 system，可同时归属某个项目，也可**无项目归属（悬浮需求）**——适用于"先于实现的跨项目能力需求"。悬浮需求可被多个项目的开发引用实现。

### 审批批次（approval batch）

所有写操作先落为待审批批次（`pending_review`），由 admin 审批：

- **自动审批**（`review_auto_process`）：三层冲突检测通过即自动入库，无需人工；
- **人工审批**（`review_approve` / `review_reject`）：检测到冲突时升级人工，admin 查看冲突详情后决定；
- **宽松模式（lax mode）**：按 Access Key 开启免审批，提交即自动处理（无冲突直接入库，有冲突仍回审批队列），适合信任度高的自动化场景；全局开关 `LAX_MODE_ENABLED` 可紧急熔断。

### Access Key 与角色（RBAC）

接入即认证：MCP 请求头 `X-MCP-Key` 携带 Key 明文，服务端 bcrypt 校验后解析出角色与权限范围。三个固定角色：

| 角色 | 职责 | 工具数 |
|------|------|-------|
| admin | 审批、密钥管理、system/项目画像管理、审计、重索引 | 29（全量） |
| pm | 需求发布与关系治理、需求检索、影响分析 | 10 |
| dev | 代码/方案/踩坑提交、资产检索、引用需求 | 9 |

权限范围两级：`projects`（资产层）与 `systems`（需求层），admin 不受限。

### 审计与幂等

- 所有工具调用记录审计日志（append-only，只增不改），按项目/操作者/工具/时间可查；
- 写操作支持 `operation_id` 幂等键：网络重试、客户端重复提交不会产生重复批次。

## 什么样的团队适合用

- 团队成员各自使用 AI 编程/办公工具（Cursor、Claude Code、TRAE 等），希望通过 MCP 协议接入；
- 有持续迭代的项目，知识（需求→实现→决策→坑）值得沉淀复用；
- 希望知识治理有门槛（审批、冲突检测）但不希望增加专职维护人力；
- 数据要求本地化部署（全部组件自托管，无外部 API 依赖，Embedding 模型内置镜像）。

技术团队规模从三五人到一个部门均可：单实例 PostgreSQL 架构，Docker Compose 一键部署，知识量增长靠 pgvector HNSW 索引与分页遍历支撑。
